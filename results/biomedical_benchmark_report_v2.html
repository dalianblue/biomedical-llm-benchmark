M3 Max·M5 Max·DGX Spark

事情是这样的——我们三个人，三台机器，两套底层方案，同时跑同一个模型（DeepSeek V4 Flash 0731）。

为了不让测试流于形式，我们攒了 9 个和日常科研强相关的生物医学任务：从基因变异检测、单细胞差异表达， 到蛋白质功能推理、文献问答和医学选择题——基本覆盖了我们平时会喂给 LLM 的各类需求。

目标很朴素：就想看看，一样的模型，换个硬件和引擎，实际用起来到底差多少？

跑完之后发现，最值得说的反而不是"谁最快"。
最让我们意外的是两个"不该变"的变量：DGX Spark 同一天上午跑和下午跑，结果不太一样；Mia 中间顺手升了个 vLLM，分数直接涨了一档。 这些事展开讲还挺有意思的，单开了一节聊（见 §04）。

01一句话结论

四份结果摆一起，最先跳出来的还是那句老话：质量由模型决定，硬件只决定你多快摸到这个上限。 你看四份的质量分，全部挤在 70.6–76.9，极差才 6 分出头；可综合分呢，从 54.9 一路冲到 73.5，差了 18 分还多。 这 18 分的鸿沟，几乎全出在吞吐和首 token 延迟上——说白了，全是硬件、引擎、调参能左右的部分。

四个关键发现
  • 质量几乎打平（70.6 → 76.9，极差才 6.3 分）——同模型同权重，硬件根本改不了答案对错。
  • 同引擎升一代芯片，等于换了台机器：M3 Max → M5 Max，吞吐中位数 10.5 → 41.3 tok/s（3.9×），TTFT 中位数 6.12s → 0.85s（7.2×），综合分直接 +18。
  • DGX 这次升级是真香：同一台机器、同一版权重，Mia 把 vLLM 方案重做一遍，综合分 67.1 → 73.5，pubmedqa 的 TTFT 从 21.59s 砸到 0.76s（28×）——看到这行的时候我是真的惊了。
  • M5 Max 综合手感最顺：吞吐 70.4 全场第一；但 DGX 升级后在质量上反超（76.9），还顺手把长 prefill 卡顿这老毛病治了。

02测试方法：九个任务都在测什么

一套生物医学标准化卷子，每个任务盯一种能力。带"质量评估"的任务都有标准答案， 能自动判分（精确率/召回率、命中检查点数、准确率）；剩下的只测吞吐和 TTFT，不评分。 所有题目都冻结在 test_data/ 里，seed=42 采样——三台机器拿到的，是同一份卷子，谁也别想赖题不一样。

任务 01
mutation_call · 序列变异检出
丢两条 BRCA1 序列给它（一条参考、一条塞了 20 个已知点突变，加起来 7088 nt × 2），让它输出 VCF 格式的变异位点。想测的是长上下文 + 核苷酸级精确对齐——结果翻车最惨的一个，后面会讲。
输入 ~15 KB · 质量：位置 P/R vs 20 个真值位点
任务 02
expression_genes · 单细胞领域知识
给 GSE100866 CD8 T 细胞里 top30 高表达的基因，让模型当"审稿人"：判断样本身份、核糖体/线粒体含量、MT-RNR2 为啥异常、QC 该关注啥。考的是单细胞生物学知识。
输入 ~1.7 KB · 开放问答，无自动评分
任务 03
expression_matrix · 表格数值推理
塞一个 20 基因 × 10 细胞的小矩阵，让它求和、求均值、找 top5、算稀疏度。听起来简单，实际是 LLM 的滑铁卢——它真的不擅长算术。
输入 ~1.6 KB · 质量：4 项子检查 vs 计算真值
任务 04
expression_code · Scanpy 代码生成
只给数据集描述，要它写一份能直接跑的 scanpy 分析脚本（读入 → QC → 归一化 → PCA/UMAP/Leiden → marker gene）。测领域代码生成——这是它最拿手的活儿之一。
输入 ~1.4 KB · 质量：12 个代码关键点检查
任务 05
protein_function · 结构生物学知识
给 BRCA1 的 p53 结合域序列加二级结构注释，问 4 个结构/功能相关的问题。纯考蛋白质结构生物学知识。
输入 ~3.3 KB · 质量：4 个子问题关键词匹配
任务 06
pubmedqa · 文献 yes/no 推理
20 道 PubMedQA，每题塞一篇摘要，让模型回答 yes/no/maybe。这是整套测试输入最长的一个（20 篇摘要 ~33 KB / ~8000 tokens），也是长 prefill 的照妖镜——后面 DGX 翻身仗全靠它。
输入 ~33 KB · 质量：准确率 vs 标注答案
任务 07
medmcqa · 医学四选一
20 道医学多选题（4 选 1），药理、解剖、病理、微生物都来一点。考医学领域知识的广度，像执业医考的迷你版。
输入 ~4 KB · 质量：准确率 vs 标注答案
任务 08
json_output · 结构化输出
给 5 个已知变异，要求按指定 JSON schema 输出。别看简单，这是 agent / 函数调用的地基——schema 稍微歪一点，下游就全崩。
输入 ~625 B · 质量：6 项 schema/正确性检查
任务 09
long_generation · 长文综述
让模型就 PARP/BRCA 啃一篇 600–800 字的英文综述。这任务就是专门为了压"持续 decode"吞吐设计的，顺便拿来算稳定性 (CV)。
输入 ~1 KB · 质量：长度 + 4 章节 + 主题覆盖 = 6 项
读这张表，记住两个"极端分子"
任务 6（pubmedqa）和任务 9（long_generation）是两个极端：一个吃 prefill（输入长），一个吃 decode（输出长）。 它俩合起来，能告诉你一台机器到底是"读得快"还是"写得快"——有意思的是，很多平台这两件事的速度压根不是一回事。 后面 DGX 升级那出戏，基本就全发生在任务 6 身上。

那到底为啥变快了？看看 Mia 动了哪几刀

根据 Mia 的开源 recipe（MiaAI-Lab/DeepSeek-v4-Flash-DSpark-2x-DGX-Spark）， 升级后的方案相比第一版，主要在四个层面动了刀：

改动 1 · 引擎层

换上 Anemll 专为 GB10 移植的 vLLM 0.25

镜像 ghcr.io/anemll/dspark-vllm-gx10:0.1.1

  • 原生带 DSpark 投机解码、NVFP4 DS-MLA KV cache、b12x MoE 后端——这三样都是冲着 GB10/Blackwell 专门做的优化
  • 第一版八成还停在接近原版的 vLLM，这些 GB10 专用路径都没接上，长 prefill 自然就吃力
改动 2 · 投机解码

开 DSpark + MTP_NUM_TOKENS=5

speculative decoding，一次验证一串草稿 token

  • decode 吞吐肉眼可见地涨——这也解释了为什么 json / medmcqa / long_generation 这类 decode-heavy 任务直接翻倍
  • 草稿块大小 5，正好跟 DeepSeek V4 的 MTP checkpoint 对齐
改动 3 · KV cache

NVFP4 DS-MLA KV cache，专治长 prefill

kv_cache_dtype=nvfp4_ds_mla

  • 低精度 KV 叠加 DeepSeek MLA 的专用路径，长上下文的显存压力和 prefill 计算量一起往下压
  • pubmedqa（8000 token 输入）TTFT 从 21.59s 砸到 0.76s，最直接的原因就在这
改动 4 · 集群与统计

2 节点 TP=2，外加 5 runs 更靠谱

recipe 名字就叫 "2x DGX Spark"

  • 两台 DGX Spark 拉成 TP=2，显存和算力直接翻倍；max_model_len 默认拉满 1M，GPU_MEM_UTIL=0.835
  • runs 从 2 加到 5，median 更稳，warmup 也更充分——第一次的数字本身就偏保守
一句话总结这次升级
Mia 没有换更好的硬件，干的事其实是把这台硬件上专门为它量身定做的软件路径，一条条全接上了。 DSpark 抬 decode 吞吐，NVFP4 DS-MLA 抬长 prefill，2 节点 TP=2 抬整体算力，5 runs 让统计更靠谱。 四件事叠一起，综合分 +6.4，pubmedqa 从灾难现场直接变冠军。也正因如此，第二次的成绩才更该作为 DGX 的代表。

05失败的任务，也要诚实写下来

做测试不是为了证明"我们牛"，是为了看清边界在哪。这套测试里有两个明显的设计翻车，四份结果都老老实实复现了—— 原原本本写在这里，给后来人避坑。

⚠ mutation_call：让 LLM 做序列比对，是典型的想当然

给模型两条 BRCA1 序列（参考 + 含 20 个已知点突变的模拟序列，共 7088 nt × 2），让它输出 VCF。当时我们的想法是："长上下文 + 核苷酸级推理"，这不就是 LLM 的甜蜜区嘛。

实际结果（四份结果出奇一致）：precision ≈ 0、recall ≈ 0、hit = 0/20（M3 Max 偶发蒙中 1 个，统计上就当它是噪声）。
模型吐出来的全是 编造的位置（100、200、300…这种连号占位符，或者 365-383 一簇假变异）， 真实的 20 个位点（205、245、261、713、…）一个都没摸到。

为什么翻车：序列比对本质是字符级精确对齐，而 LLM 的注意力机制对"逐位比较两条 7000 字符的长串"天生不在行。 它学到的只是"VCF 长什么样"，根本不是"怎么真的做比对"。

正确姿势：这类活儿交给 BLAST / BWA / minimap2 这些专用对齐工具，LLM 只负责写报告、解读结果就好。说白了，我们把"工具该干的活"误判成了"LLM 该干的活"。

数值推理（expression_matrix 1/4 ~ 2/4）
让模型从 20×10 的小表里做求和、找差异、算倍数变化。四份结果都只蒙对 1–2 个检查点。LLM 不擅长精确算术，这早就是行业共识了。 正确姿势：让 LLM 写 pandas 代码（去看 expression_code 任务，9–12/12 的高分），让 Python 去算，它算得比谁都准。
但有些任务，稳得让人踏实
Scanpy 代码生成（9–12/12，DGX 升级后直接满分）、结构生物学知识（4/4 全场满分）、 JSON schema 输出（6/6 全场满分）、医学 MCQ（85% 全场齐平）、 长文综述（6/6 全场满分）——你会发现一个共同点：这些任务都是把 LLM 当"知识 + 语言"引擎在用，而不是当"计算 + 对齐"工具在使。

06翻车现场，和反杀现场

四份结果里，有两个故事最值得拎出来念叨：一个是 M3 Max 在长输入上的翻车现场，另一个是 DGX 升级怎么把同样的翻车扭成了招牌。

M3 Max 在长 prefill 上，基本没法用
M3 Max + ds4-server 在 pubmedqa（8000 token 输入）上，TTFT 52.26 秒、吞吐 1.35 tok/s； 换到 mutation_call（6820 token 输入），TTFT 43.03 秒。 但短输入任务（medmcqa 才 4KB）TTFT 只有 0.057s——快得飞起。问题全卡在长 prefill 这一条路上。

这真不是"老芯片所以慢"，而是 ds4-server 在 M3 Max 上的 long-context kernel 压根没调好。同款引擎放到 M5 Max 上，pubmedqa TTFT 立刻就降到 2.57s。 一句话：引擎 × 芯片的耦合调优，往往比芯片代际本身还重要。
DGX 升级，把软肋硬生生掰成了强项
还是同一台 DGX Spark：升级前 pubmedqa TTFT 21.59s（全场倒数第二），升级后 0.76s（直接全场第一）。 这事说明一个道理：很多时候所谓"硬件不行"，真相是"软件没配对"。GB10 不是跑不动长 prefill， 它只是需要 NVFP4 DS-MLA 这种为它量身打做的 KV cache 路径，才能把劲使出来。

08给想自己搭本地 LLM 的你

四份结果，外加一次升级前后对照，揉碎了挤出 7 条经验。不敢说是真理，但都是真踩过的坑。

  1. 模型决定质量上限，硬件只决定你多快够到这个上限 四份质量分 70.6–76.9（极差 6.3），综合分却 54.9–73.5（极差 18.6）。差距全长在速度上。 所以，想提升答案质量？换模型，别换机器——换机器救不了答错的题。
  2. 引擎 × 芯片的调优，比芯片代际差距还大 M3 Max → M5 Max，同引擎升一代：吞吐 3.9×。 DGX 升级前后，同机器换引擎配置：pubmedqa 吞吐 14×、TTFT 28×。 所以记住："硬件不行"这锅，很多时候是软件没配对替它背了。
  3. 长上下文 ≠ 长上下文跑得快 能装下 256K tokens，不等于在上面跑得动。prefill 阶段对硬件的压力特别大—— M3 Max 在区区 8K 输入上 TTFT 就能崩到 52s，DGX 升级前也崩到 21s。买之前一定看真实的长上下文 benchmark，宣传页上那个 ctx size，看看就好。
  4. speculative decoding，GB10/Blackwell 上的必开开关 DSpark + MTP_NUM_TOKENS=5 一开，DGX 的 decode 吞吐直接翻倍。这种"免费午餐"级别的优化，部署时千万确认它真的打开了，别白扔一半性能。
  5. 任务设计，一定要扬长避短 LLM 擅长：知识问答、代码生成、结构化输出、长文写作、文献推理。 LLM 拉胯：字符级精确比对、纯算术、严格逻辑链。把拉胯的那些活儿外包给工具（BLAST、pandas、regex、SQL），让 LLM 干它本来就在行的。
  6. runs 要跑够，warmup 要做足 DGX 头一次只有 2 runs，数字偏保守；第二次 5 runs 之后多个任务明显回升——这里面有一部分就是统计更稳、warmup 更充分带来的。 正式 benchmark 至少 3–5 runs，头一趟当 warmup 直接丢掉，别心疼。
  7. 说句掏心窝的：云 API 还是大多数人的最优解 除非你有硬性需求（数据合规、离线、长期高频调用、纯粹研究兴趣），否则按 token 付费的云 API，在多数场景下比本地硬件便宜得多。 本地 LLM 真正值钱的地方是数据私有 + 可重复 + 无审查——从来就不是"省钱"。
