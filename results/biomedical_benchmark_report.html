03失败的任务，也要诚实写下来

做测试不是为了证明"我们牛"，是为了看清边界。这套测试里有两个明显的设计失误， 我们原原本本记录在这里，给后来人避坑。

⚠ mutation_call：让 LLM 做序列比对，是典型的想当然

任务设计：给模型两条 BRCA1 序列（参考序列 + 模拟突变序列，共 7088 nt × 2，含 20 个已知点突变）， 让它输出 VCF 格式的变异位点。我们以为"长上下文 + 核苷酸级推理"是 LLM 的甜蜜区。

实际结果：两台机器 precision = 0, recall = 0, hit = 0/20。
模型输出的全是 编造的位置（chr17:1, chr17:2, chr17:3 … 连号占位符）， 而真实的 20 个突变位点（205, 245, 261, 713, …）一个都没找到。

为什么会失败：序列比对本质是字符级精确对齐，LLM 的注意力机制对"逐位比较两条 7000 字符的字符串" 天然不擅长。它学会的是"VCF 长什么样"，而不是"怎么真的做比对"。

正确做法：这类任务应该用 BLAST / BWA / minimap2 等专用对齐工具，LLM 只负责生成报告和解读结果。 我们把"工具能干的活"误判成了"LLM 能干的活"。

数值推理（expression_matrix 1/4 ~ 2/4）
任务要求模型从 20×10 的表达矩阵里做求和、找差异、计算倍数变化。 两台机器都只命中 1-2 个检查点。LLM 不擅长精确算术， 这是行业共识，但我们仍然把它放进了测试——结果就是难看的低分。 正确姿势：让 LLM 写 pandas 代码（看 expression_code 任务，10-11/12 高分），让 Python 去算。
但有些任务表现超出预期
Scanpy 代码生成（10-11/12）、结构生物学知识（4/4）、 JSON schema 输出（6/6）、医学 MCQ（85%）、 长文综述（6/6）——五个任务满分或接近满分。 这些任务的共同点：把 LLM 当成"知识 + 语言"引擎，而不是"计算 + 对齐"工具。

04一个值得警惕的异常点

DGX Spark 在 pubmedqa 上表现极其异常：吞吐 2.15 tok/s，TTFT 高达 21.59 秒。 同一个任务 M5 Max 是 17.77 tok/s + 2.57 秒 TTFT。为什么差这么多？

长上下文 + 长 prefill = NVIDIA 的软肋（在这台机器上）
pubmedqa 的输入是 20 篇 PubMed 摘要，约 33 KB / ~8000 tokens。 DGX Spark (GB10 Grace+Blackwell) 在 vLLM 上对长 prefill 的处理明显吃力：
  • TTFT 21.59s vs M5 Max 的 2.57s —— DGX 花 19 秒在 prefill 阶段
  • 吞吐 2.15 tok/s vs M5 Max 的 17.77 —— decode 阶段也被拖累
  • 同样的输入、同样的模型、同样的 prompt，两台机器的体验差了 ~8 倍
可能原因：vLLM 在 GB10 上的 attention kernel 对长序列未充分优化， 或 KV cache 配置导致频繁换页。不是模型差，是引擎+硬件的耦合没调好。

提示：短上下文任务（medmcqa 4KB、json 625B）上 DGX 表现正常， 说明问题集中在长 prefill 路径，不是普遍性慢。

06给想自己搭本地 LLM 的你

我们踩过的坑、想明白的事，浓缩成 7 条。不是真理，是经验。

  1. 模型决定质量上限，硬件只决定到达上限的速度 这次实验最干净的结论：同模型换硬件，质量 sub-score 差 ±5 分以内（71.7 vs 75.8）， 但吞吐可以差 1.5 倍以上。想提升答案质量？换模型，不是换机器。
  2. 128GB 内存是入场券，不是性能差异点 两台都是 128GB，都跑 256K 上下文无压力。内存够用之后，瓶颈就转移到 GPU 算力、kernel 优化、引擎调度上了。 别为"32GB 还是不够"焦虑——确认你的模型大小（~4 bit 量化下 70B 模型约 35GB），加 30% 余量就是你的内存下限。
  3. 引擎比硬件更影响体验 我们还有一台 M3 Max 用 ds4 CLI 二进制跑同样测试，慢了 5.7 倍（6.5 vs 36.9 tok/s）。 同芯片、同模型、换引擎，差距比换芯片还大。选引擎时多看 benchmark，少看营销。
  4. 任务设计要扬长避短 LLM 强在：知识问答、代码生成、结构化输出、长文写作、文献推理。 LLM 弱在：字符级精确比对、纯算术、严格逻辑链、确定性搜索。 设计测试或工作流时，把弱项外包给工具（BLAST、pandas、regex、SQL），让 LLM 做它擅长的部分。
  5. 长上下文 ≠ 长上下文快 能装下 256K tokens，不等于能在 256K 上跑得快。prefill 阶段对硬件压力大， DGX Spark 在 8K tokens 输入上 TTFT 就崩到 21 秒。买之前看真实长上下文 benchmark，别只看宣传的 ctx size。
  6. 测试要测"真实任务的失败"，不只测"能完成的任务" 我们这套测试最大的价值不是 9 个高分，而是诚实记录了两个失败任务（mutation_call、expression_matrix）。 这些边界告诉你"什么时候必须用别的工具"，比一堆满分更有参考价值。
  7. 云 API 仍然是大多数人的最优解 除非你有硬性需求（数据合规、离线、长期高频调用、研究兴趣）， 否则按 token 付费的云 API 在多数场景下比本地硬件便宜得多。 本地 LLM 的真正价值在数据私有 + 可重复 + 无审查，不在"省钱"。
